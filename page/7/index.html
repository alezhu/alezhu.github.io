Visual C# 2010 Express + MS SQL Server (Express)

Visual C# 2010 Express + MS SQL Server (Express) Столкнулся с особенностью Express версии Visual Studio 2010 (наверняка в ранних экпрессах тоже самое) - в качестве источника данных (Data Source) Visual C# Express предлагает на выбор только источники, работающие с файлом, а не с сервером. Вот так это выглядит: В то же время в Visual Web Developer 2010 Express ( и в VS2005 Pro тоже ) список выглядит так: Как видите, список побогаче. Вначале я решил было, что Visual C# переглючило, и стал искать возможность получить список источников данных, аналогичный тому, что есть в Web Developer. Переустановка ни к чему не привела. Тогда я нашел место, где в реестре хранится этот список для Visual WD Express - это тут HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\VWDExpress\10.0\DataSources. Я его скопировал в HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\VCSExpress\10.0\DataSources - для VC#Express. Но это ничего не дало. В ходе экспериментов выяснилось, что похоже список возможных источников данных зашит где-то в самом VC#Express. Откуда такие данные? Очень просто - допустим VC#Express берет все источники из реестра и как-то проверяет что это файловый источник, а не серверный. Тогда берем и перименовываем в реестре GUID одного из файловых источников - я менял {485C80D5-BC85-46db-9E6D-4238A0AD7B6B} на {485C80D5-BC85-46db-9E6D-4238A0AD7B6C}. Если бы наше допущение было верным - то количество источников не поменялось бы. Но это не так - Microsoft SQL Server Database File исчезает (это его GUID я менял) из списка. Также я пытался копировать ветку реестра с этим GUID - дубликат источника не появлялся. Кроме того, выяснилось что VC#Express не проверят файловый ли это источник. Как это проверить? Опять же просто - берем GUID серверного Microsoft SQL Server {067EA0D9-BA62-43f7-9106-34930C60C528} и меняем его на GUID Microsoft SQL Server Database File {485C80D5-BC85-46db-9E6D-4238A0AD7B6B} - и, о чудо!, в списке источников данных теперь вместо файлового источника - серверный: Но чуда на самом деле нет. При попытке выбрать этот источник - все равно появляется окно выбора файла с базой даннных: а не выбора сервера и базы данных на нем, как должно бы было быть: К сожалению, в недрах Visual C# 2010 Express мне не удалось найти место, где забита эта логика, так что я оставил попытки что-то тут изменить. Кому не лень копать - дерзайте =) Позже в интернете я нашел упоминания подобной проблемы у других людей, и оказалось, что это совсем не проблема, а такая “фича” всех компонентов Express версии. То есть типа хотите сервер - покупайте нормальную Visual Studio. Но есть одно но - “фича” не распространяется на Visual Web Developer 2010 Express - в нем то все нормально с подключением к серверам. И это как говорится “доставляет”. А почему - расскажу ниже. Итак, что у нас в результате. У нас есть VC#Express, на котором мы хотим писать Windows приложение, которое должно подключаться к MS SQL Server. Рекурсивный Application Data

Рекурсивный Application Data В Vista компания Microsoft “перекроила” ссылки на пользовательские данные. Если раньше все лежало в Documents and Settings, то теперь все не совсем так. Например, вместо Documents and Settings используется Users, а первый сделан как символическая ссылка на второй. А вот Documents and Settings\All Users лежит в ProgramData прямо в корне системного диска. При этом чтобы не нарушить работу старых приложений, которые про новую моду ничего не знают, сделана куча символических ссылок со старых “мест работы” на новые. И в частности есть рекурсивные ссылки, то есть такие ссылки, которые лежат внутри какого-либо каталога и ссылаются на него же. Далеко ходить не надо - ProgramData\Application Data ссылается на сам ProgramData. Таким образом, хотя, например, данные приложений Microsoft для всех пользователей лежат фактически в ProgramData\Microsoft\* старое приложение будет их искать по пути Documents & Settings\All users\Application Data\Microsoft\*. Но благодаря тому что, D&S ссылается на Users, а Users\All users ссылается на ProgramData, а ProgramData\Application Data ссылается на сам ProgramData - мы попадем туда где фактичеки данные и лежат. С такими ссылками возникает проблема при поиске. То есть приложение (например, Total Commander), которое что-то ищет в Users и его подпапках попадает на Application Data, не разбирает, что это ссылка ведущая как бы назад, и снова начинает в ней искать - хотя поиск там уже был. И в итоге получается мы залезаем в вот такие вот дебри: c:\Users\All Users\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data\Application Data.… Как с этим бороться? Сдвиг параметров в командных файлах

Сдвиг параметров в командных файлах Итак, задача. Пишете вы “батник” (командный файл - с расширением bat или cmd). В этом батнике вы вызываете какую-нибудь программу по длинному пути и передаете в нее кучку постоянных параметров. Но при этом есть еще несколько параметров той программы, которые в батнике не заданы и должны задаваться как параметры при вызове самого батника. Чтобы было понятнее, пример. Итак нам нужно вызвать SQLMetal для генерации файла с кодом на C# по какой-либо базе данных. Так вот мы хотим имя базы данных и файл для вывода задавать в параметрах батника. Таким образом, имеем батник sqlmetal.cmd следующего содержания (все записано в одну строку): "c:\Program Files\Microsoft SDKs\Windows\v7.0A\bin\SqlMetal.exe" /server:.\sqlexpress /language:csharp /pluralize /database:%1 /code:%2 Чудесно. Запускаем скажем sqlmetal.cmd northwind northwind.cs и получаем в каталоге запуска файлик northwind.cs, со всем необходимым. Но на самом деле не со всем. Там, скажем, нет кода для вызова хранимых процедур. И допустим вот запонадобились нам эти процедуры. И чтобы они там были нужно передать в sqlmetal.exe еще пару параметров - /sprocs и /functions. Как быть с батником - ведь добавив при его вызове эту пару параметров мы ее потеряем при вызове sqlmetal.exe, потому что нигде не указано, что надо передавать еще что-то кроме первых двух? Ну, естественно, батник можно тупо переписать, добавив параметры, но это не спортивно и не всегда эти процедуры нужны. Можно копию его сделать с вызовом процедур, но это тоже все не универсально. Что еще? Ну, мы знаем что есть параметр %*, который возвращает все переданные в батник параметры, и что есть команда shift, которая сдвигает эти параметры влево на 1,так что %2 становится %1, %3 становится %2 и так далее. %1 теряется, но его можно заранее сохранить в переменую. Вроде бы просто - сохраняем первые 2 параметра в переменные, делаем 2 shift’а и передаем оставшиеся в %* в sqlmetal.exe. Засада в том, что shift на переменную %* не влияет - та всегда содержит все параметры. =( Вообще есть простой тупой способ решить задачу - перечислить все параметры, начиная с %3, ибо их немного: sqlmetal.exe ... /code:%2 %3 %4 %5 %6 %7 %8 %9 Но тут новая засада - проблема как раз в том, что их немного - всего 9 (да, первые 2 мы зарезервировали, но shift’ом это можно поправить). Что если параметров будет передаваться больше? Очевидно надо в цикле брать параметры по одному начиная с нужного и объединять их в новую переменную. Такое решение было найдено тут http://stackoverflow.com/questions/761615/is-there-a-way-to-indicate-the-last-n-parameters-in-a-batch-file .
